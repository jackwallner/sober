## Section 2 — Rev B: review funnel + conversion-surface audit

### 2a. Review funnel

Shared pattern followed correctly: **enjoyment gate at a positive moment → explicit "Rate?" → native `requestReview()` only as a fallback, with a direct App Store write-review link as the primary path.**

- **Trigger moments** (`recordPositiveMomentForReview()`, `HomeView.swift:386-389`), fired from three genuine value moments: dismissing a garden growth celebration (`HomeView.swift:133`), the "Still sober" welcome-back backfill action (`HomeView.swift:251`), and completing a check-in (`HomeView.swift:314`). All three are demonstrated-value moments, not blind timers.
- **Gating** (`Shared/Services/ReviewPromptTracker.swift`): requires `minimumLaunchCount` (5 release / 2 debug), `minimumPositiveMoments = 3`, `minimumDaysSinceFirstOpen = 7`, and a 120-day cooldown after any prompt is shown. Reasonable friction against asking too early.
- **Flow** (`Sober/Views/ReviewPromptSheet.swift`): `.enjoyment` ("Is Sober helping...?") → "Yes" leads to `.reviewPitch` which opens a direct App Store write-review URL (`Shared/Utilities/AppStoreReviewLinks.swift`, storefront-aware); "Maybe later" at that step instead sets `pendingNativeReviewAfterDismiss = true` (`HomeView.swift:413-418`), and native `requestReview()` (`@Environment(\.requestReview)`) fires on sheet dismiss (`HomeView.swift:151-158`). "Not really" at the first step routes to a mailto feedback draft instead of a review ask.
- **Settings row**: confirmed present — `SettingsView.swift:139-141`, "Rate or Send Feedback" → `ReviewPromptCoordinator.shared.requestEnjoymentPrompt()`.

This matches the required shared pattern faithfully. No issues found.

### 2b. Conversion-surface map (every trial/paywall trigger)

Central plumbing: `Sober/Features/Paywall/BloomFeature.swift` (`TrialOfferCoordinator`, `TrialSubsequentPitchGate`, `TrialNudgeGate`), consumed from `Sober/App.swift`'s `MainTabView.handleTrialPitch(_:)` (App.swift:201-278).

| Surface | Trigger | Cooldown / cap | Value moment or blind timer? |
|---|---|---|---|
| Onboarding trial step | Reached only if `trialEligible` at the last onboarding step (`OnboardingView.swift:214-271`); calls `TrialNudgeGate.markShown()` on appear | One-time, part of setup flow | Explicit setup step, not a surprise interrupt. CTA geometry matches every other onboarding step (`bottomBar`, OT710 Rev A). |
| Post-onboarding Home popup | `AppGroup.postOnboardingPaywallKey`, only set if the onboarding trial step was *not* reached (`OnboardingView.swift:510-528` `finishOnboarding`); 700ms delay on first Home arrival (`HomeView.swift:364-384`) | Mutually exclusive with the onboarding trial step (one or the other, never both) | Day-0 blind timer, but deliberately deduplicated against the onboarding step so it can't double-pitch the same session. |
| Passive tab nudges | `.task { presentPassiveTrialNudge(..., intent: .postOnboarding, delay: 6) }` on Home (`HomeView.swift:122`); similar passive nudges on Timeline/Health tab appear (per `BloomFeature.swift` intents) | Global `TrialNudgeGate` schedule: `[20, 28, 44, 96, 168]` hours, shared across *all* passive-style pitches | Blind timer in isolation, but the shared global cooldown means only one passive-style pitch can fire roughly once a day at first, backing off to weekly — meaningfully throttled. |
| Usage-based: 3rd check-in | `recordCheckInForTrialPitch()` (`HomeView.swift:426-438`), persisted count, 2.5s delay after the 3rd check-in ever | Shares the same global `TrialNudgeGate` gate | Value moment (3-day habit forming). |

| Usage-based: Journal tab visits | `JournalView.swift` `onAppear` increments `AppGroup.journalTabVisitCountKey`, fires on 2nd+ non-Pro visit, 2s delay | Shares the same global `TrialNudgeGate` gate | Borderline — tied to browsing a locked feature repeatedly, not a pure timer. |
| Locked-feature taps (Journal compose, Health full detail, garden species swap, achievement detail) | `requestSubsequentLockedFeaturePitch(_:)` fires immediately on tap; 1st tap per intent shows the full `PaywallView` directly, 2nd+ tap (persisted count) shows the softer `TrialOfferSheet`, capped at `maxTrialPitchesPerIntentPerSession = 2` | Persisted count per intent (`AppGroup.bloomActionCountKey(for:)`), session cap 2 | User-initiated (they tapped a locked thing) — expected, not surprising. |
| Settings "Upgrade" | Explicit tap, `.explicitUpgrade` policy (`SettingsView.swift`) | None needed — explicit request | Fully user-initiated. |

**Overall assessment**: the surface count looks large on paper, but nearly every *passive* trigger (post-onboarding popup, tab-appear nudges, check-in/growth/journal usage nudges) funnels through the single global `TrialNudgeGate` cooldown, so an engaged daily user in practice sees at most one unprompted pitch roughly once a day early on, decaying to about once a week. Only the *locked-feature-tap* and *explicit-upgrade* surfaces bypass that shared gate — and those are directly triggered by the user tapping something gated, which is expected paywall behavior, not spam.

**Flag**: one concrete defect found while mapping this (not a policy problem, a timing bug) — see Section 3, "Review prompt and trial-pitch sheets can race."

## Section 3 — New findings

### Bugs

**1. Review prompt and trial-pitch sheets can race and double-present — P1**
`HomeView.swift:133-135` fires both `recordPositiveMomentForReview()` and `scheduleTrialPitchAfterGrowthCelebration()` synchronously from the same `GrowthCelebrationView` dismiss closure. `scheduleTrialPitchAfterGrowthCelebration()` (`HomeView.swift:440-451`) dispatches `evaluateUsageBasedTrialPitch(..., delay: 1.5)`, which — if the growth-celebration usage count has reached its threshold — sets `TrialOfferCoordinator.shared.pendingRequest`, observed by `MainTabView.onChange(of: trialCoordinator.pendingRequest)` (`App.swift:153-156`) which sets `showTrialOffer`/`showTrialPaywall = true` (`App.swift:123-124`) and presents a `.sheet` attached at the `MainTabView`/TabView level (`App.swift:163,189`) — an ancestor of `HomeView`.

Separately, `recordPositiveMomentForReview()` posts `.soberPositiveMomentForReview`, received by `HomeView.swift:159-160`, calling `scheduleReviewPromptAfterPositiveMoment()` (`HomeView.swift:391-411`), which after a 3.5s delay sets `showReviewPrompt = true`, presenting a *second*, independent `.sheet` attached directly on `HomeView` (`HomeView.swift:151-158`).

Both guards (`HomeView.swift:394-397` and `401-405`) only check `showGrowth`, `showCheckInDetail`, and `showReviewPrompt` — none of them are aware of `MainTabView`'s `showTrialOffer`/`showTrialPaywall`. For an engaged user experiencing their 2nd+ stage-up celebration (the threshold at which the growth-celebration trial pitch is eligible) while also satisfying the review-prompt gates, this produces two independent `.sheet(isPresented:)` calls going true within ~2 seconds of each other from two different view layers — SwiftUI will either silently drop one, log "Attempt to present ... while a presentation is in progress," or show a broken transition. **Fix**: give `TrialOfferCoordinator` (or a small shared `PresentationCoordinator`) a single source of truth both `HomeView` and `MainTabView` check before presenting, or route both the review sheet and the trial sheet through the same view layer so they share one mutex.

**2. Settings start-date edit doesn't backfill the calendar — P2**
`SettingsView.swift:208-216`'s `startDateBinding` calls only `SobrietyService.updateStartDate($0)` (`SobrietyService.swift:34-38`, which just clamps and sets `journey.startDate`) and `WidgetSnapshotPump.push`. It never calls `CheckInService.fillJourney`. The only place that runs `fillJourney` is `HomeView.onAppear` (`HomeView.swift:115`), and because `MainTabView`'s `TabView` keeps tab content alive across reselection, `HomeView.onAppear` won't refire just from switching back to the Home tab after a Settings edit within the same app session — so the day counter (journey-start-based) and the calendar (check-in-based) can visibly disagree until the next cold launch. This is exactly the class of trust bug c521 Item 4 called out, reopened by a code path the original fix didn't cover. **Fix**: call `CheckInService(context: context).fillJourney(start: newDate, through: DateHelpers.daysAgo(1))` inside `startDateBinding`'s setter, same as `HomeView.onAppear` does.

**3. `GardenService.setBonsaiStyle` has no entitlement check — P2 (defense-in-depth)**
`Shared/Services/GardenService.swift` `setBonsaiStyle(_:)` writes `activeBonsaiStyleID` unconditionally; the Bloom+ gate is enforced only in the UI (`Sober/Features/Garden/GardenCustomizationView.swift`, blur+lock+`canUseSpecies(id:isPro:)` check before calling the service). Any other call site — including a future one, or anything driven by `AppIntent`/widget interactivity per c521 Item 13's suggestion — would bypass the gate entirely since the service itself never re-checks `isPro`. **Fix**: move the `canUseSpecies` check into `GardenService.setBonsaiStyle` itself so gating survives regardless of call site.

**4. `recordCheckInForTrialPitch` reuses the `.postOnboarding` intent — P2 (minor, code-quality)**
`HomeView.swift:426-438` fires the 3rd-check-in trial pitch under `intent: .postOnboarding` — the same intent as the actual post-onboarding popup — rather than a distinct intent (e.g. a hypothetical `.checkInMilestone`). Since `TrialSubsequentPitchGate`'s per-session pitch cap and `focusFeature` mapping are keyed by intent, this means the check-in nudge always renders the generic (no-`focus`) pitch copy and shares its session budget with the day-0 popup, which is probably fine functionally but makes the two logically distinct triggers indistinguishable in the pitch UI and in any future analytics keyed by intent. Not urgent, but worth a dedicated intent case if these ever need to be tuned independently.

### UX

**5. Notifications carry no personalization or deep-link — P2**
Confirms c521 Item 12 as still open. `NotificationService.swift:16-35` sends one of two fixed strings with no `userInfo`, no notification category/actions, and there is no `UNUserNotificationCenterDelegate` anywhere in the app (repo-wide grep confirmed), so tapping the notification just foregrounds the app to whatever tab was last open rather than jumping to Home/check-in.

**6. Widget/Watch remain view-only — P2**
Confirms c521 Item 13 as still partially open. Both `SoberWidgets/SoberWidgets.swift` and `SoberWatch/SoberWatchApp.swift` correctly self-refresh the day count live (no staleness bug), but neither offers a check-in action — `SoberWidgets.swift`'s widget is `StaticConfiguration` only, and `WatchRootView` is display-only. `WidgetSnapshotPump.swift` already computes everything an `AppIntent`-driven check-in write-through would need.

**7. `gardenThemeID` is a dead, user-facing-sounding field — P3**
Confirms c521 Item 17. `Shared/Models/GardenState.swift` still stores `gardenThemeID` (default `"zen"`) with no reader anywhere in the UI. Low risk (nothing currently promises it to the user in copy), but it's schema debt worth deleting or wiring up before it's rediscovered.

## Section 4 — Prioritized fix list

1. **Fix the review-prompt / trial-pitch sheet race** (Section 3 #1) — the only concretely reproducible P1 bug found; both view-layer state flags need a shared presentation mutex. *Shared code (`TrialOfferCoordinator`/`BloomFeature.swift` pattern lives in `Sober/Features/Paywall/`, not `Shared/`, so this is app-specific to Sober and would need to be re-derived for `nicfree` rather than ported directly — but `nicfree` almost certainly has the same architecture and should be checked for the identical race.)*
2. **Backfill the calendar on Settings start-date edit** (Section 3 #2) — one-line fix in `SettingsView.startDateBinding`, reopens a P0-adjacent data-trust bug from c521 Item 4. **Shared code**: `SobrietyService.swift`/`CheckInService.swift` exist verbatim in `nicfree/Shared/Services/`, so this fix (and the underlying pattern) ports directly.
3. **Move `canUseSpecies` gating into `GardenService.setBonsaiStyle`** (Section 3 #3) — defense-in-depth, cheap, prevents future bypass. `GardenService.swift` is `Shared/`; ports to `nicfree` if it has an equivalent species/customization service.
4. **Add App Intent check-in to widget/watch** (c521 #13 / Section 3 #6) — highest-leverage remaining friction item per c521's own priority matrix (P2, "friction reduction"); `WidgetSnapshotPump` already has everything needed. Widget/watch targets are app-specific but the underlying `WidgetSnapshotPump.swift`/`WidgetSnapshot.swift` pattern is `Shared/` and ports.
5. **Personalize + deep-link notifications** (c521 #12 / Section 3 #5) — rotate copy with live streak data, add a "Check in now" category action, deep-link to Home. `NotificationService.swift` is `Shared/` and ports directly.
6. **Allow one free Journal entry before gating compose** (c521 #11, still OPEN) — matches the "taste early wins" pattern already used successfully for Health (first 5 benefits free).
7. **Add Journal edit-in-place** (c521 #10, still PARTIAL) — detail/delete already shipped; editing is the remaining gap.
8. **Give the onboarding trial step (or a dedicated final step) an explicit free-vs-Bloom+ comparison** (c521 #16, PARTIAL) — sets expectations before the first mid-app paywall hit.
9. **Delete or wire up `gardenThemeID`** (c521 #17 / Section 3 #7) — small cleanup, `Shared/Models/GardenState.swift` ports to `nicfree` if it carries the same dead field (worth a quick grep there).
10. **Split the `.postOnboarding` intent reuse for the check-in trial pitch** (Section 3 #4) — low urgency, improves pitch-copy targeting and analytics clarity.
11. **Give a dedicated Progress/Collection entry point** (c521 #7, PARTIAL) — two entry points now exist; a persistent Home-surface affordance (chip/badge) would finish this off per c521's original suggestion.
12. **Extend the Bonsai-quality art treatment to Health/onboarding/celebration chrome** (c521 #18, PARTIAL) — `BonsaiRenderer.swift` proves the team can do custom illustration; next highest-value target per c521 is Health benefit icons and one celebration illustration.

Items already fully resolved and *not* re-flagged: c521 #1, #2, #3, #6, #9, #14, #15, #19, #20 (see Section 1 for evidence). c521 #5 and #8 are obsolete due to the garden-decoration system removal and the pan/viewport redesign, respectively — no action needed.
