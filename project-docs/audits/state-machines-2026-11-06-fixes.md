## Held for Jack

- **Repair for users who already hit J3.** The fix stops new stale rows. Users who moved their start later before this build still have assumed rows before their first run, inflating lifetime days, money and calories, and Timeline can't reach them. Those rows can't be told apart from real taps logged by builds before `wasLogged` existed, so a cleanup could delete check-ins a long-time user really made. The same limit applies to the fix itself: when a user moves the start later, a sober day they tapped in a build before `wasLogged` (added 2026-09-03), with no mood or note, falls inside the dropped range and goes with the assumed rows. Decision: run a one-time cleanup of unlogged, mood-less, note-less rows before the earliest run start, or leave existing data as it is?

Not held, but worth knowing: N3's fix queues 30 days of dated reminders. Someone who doesn't open the app for 30 days stops getting the daily one until they return (the lapse nudge still reaches them at day 3). A repeating request can't carry changing copy, so this was the trade.

## Second regression check follow-up

[The second verify pass](state-machines-2026-11-06-verify.md) found one crash: after "I slipped" on yesterday and a zone change west within the first hours of the day, Z1 re-keys the new run's start to the new zone's midnight of that date, which is after now. `earliestStartDate()` returned `min(bound, active.startDate)`, both later than now, and `SettingsView.swift:64` built `earliest...Date.now`, which traps. Fixed in "fix: keep the Settings start floor at or before now after a zone change": `earliestStartDate(now:)` returns `min(bound, active.startDate, now)` (`Shared/Services/SobrietyService.swift:83`). The re-key itself is left as is: the run's start stays on its calendar day, as the rows do, and the counter reads that day honestly. The probe is now `j4_theStartFloorNeverPassesNowAfterAZoneChange`, built on the state the re-key leaves (a slip-closed run ending today, the active run starting at the next midnight), with a control that the start is after now.

## Third regression check follow-up

[The third verify pass](state-machines-2026-11-06-verify.md) found that S1's undo rule and J4's trim together refused the next slip's undo. `trimClosedJourneys` leaves a Reset or leftover onboarding run that began after the moved start empty on its own start, the latest start of any closed run, and `reversibleSplit` took it as "the run before" and refused because no slip closed it. While turning its probes into tests, a control turned up a second route with the same cause and no start move. The run older onboarding builds left behind shares the active run's start and ends at the moment setup ran, so it sorted after the active run once a slip closed that run on an earlier day. Route: a user who onboarded before 2026-10-31 logs a forgotten slip from before their setup date, then undoes it. 7199ab0 matched on the end date and allowed that undo. Fixed in "fix: let a slip be undone past a Reset or leftover onboarding run". `reversibleSplit` now takes the slip-closed run ending on the day, and refuses only if another closed run began after it. Empty runs not closed by a slip are passed over (`Shared/Services/SobrietyService.swift`, `reversibleSplit`). All four S1 tests still refuse their routes, because a later slip or a Reset always starts a run after the slip's run. The verify pass's three probes are now `j4_s1_` tests. Two more were added: `j4_s1_aBackDatedSlipBeforeTheTrimmedRunIsUndoable` (a slip back-dated before the trimmed run's start) and `s1_aLeftoverOnboardingRunDoesNotBlockUndoOfASlipBeforeSetup`. The control `control_leftoverOnboardingRunThenSlipTodayIsUndoable` covers the no-move case.

## Fifth regression check follow-up

[The fifth verify pass](state-machines-2026-11-06-verify.md) found that S1's rule refused the most recent slip for a user whose setup was killed after the trial step and redone on a later launch, on a build before 2026-10-31. The redone setup re-picked an earlier date (or the same date at an earlier hour), so the first pass's run starts after the user's active run and ended when setup ran again. `reversibleSplit` refused whenever any closed run started after the slip-closed run, and this leftover qualifies although it sits inside the user's run. Route: Home › ⋯ › I slipped › Log, then Timeline › today: "Change to sober" is replaced by the "most recent one" refusal, though it is the only slip. 9733bc3 allowed that undo.

Fixed in "fix: let a leftover onboarding run inside the user's run not block a slip undo". The verify doc suggested blocking only on runs that start at or after the slip run's end. That alone still refused a slip back-dated to before the leftover's start (the leftover then starts after the slip and runs on into the active run), so a blocker must also end by the active run's start: it has to lie between the slip and the active run (`Shared/Services/SobrietyService.swift`, `reversibleSplit`). A later slip and a Reset after the slip always do, so the four `s1_` refusal tests keep their meaning. Both verify probes are now regression tests (`s1_leftoverRunStartingLaterSameDateThenSlipTodayIsUndoable`, `s1_leftoverRunStartingLaterEarlierDateThenSlipTodayIsUndoable`), plus `s1_aSlipBackDatedBeforeALaterLeftoverRunIsUndoable` for the back-dated route. One shape is still refused: a leftover that began and ended on the very day a slip is back-dated to, after the active run began. 9733bc3 picked that leftover as the run to reopen (latest start ending on the day), which would have reopened the wrong run, so refusing is the safer of the two and no worse than shipped.

Verify note 4 (J1's split takes `journeys.first` of an unsorted fetch, so a back-dated slip in a day both the user's run and a leftover span could split the leftover and leave the user's run counting through the slip) shares the cause, so it is fixed too, in "fix: split the user's own run, not a leftover one, for an older slip". `splitClosedJourney` now prefers the slip-closed spanning run, else the one that ended last (a leftover ended when setup ran, before any Reset). `j1_anOlderSlipSplitsTheUsersRunNotALeftoverOne` inserts the leftover first so the unsorted fetch returns it first, and checks the longest streak (60, not 91) and the newer slip's undo (70, not 101).

## Sixth regression check follow-up

[The sixth verify pass](state-machines-2026-11-06-verify.md) found that J4's trim and J3's cleanup together made a Settings start edit one-way. Moving the start back past a Reset trimmed the Reset run's end in the store; moving it forward again then let J3 delete the Reset run's assumed days, and nothing gave back the run's end. Lifetime days, money and calories dropped by the gap, and the best streak shrank to the trimmed run. 9733bc3 kept both.

Fixed in "fix: make a Settings start edit reversible, a Reset run is cut at read time", as Jack directed (2026-11-07):

- `updateStartDate` no longer writes to closed runs. `SobrietyService.effectiveEnd(of:among:)` reads a closed run as ending at the start of the run laid over it (a run that starts before it ends and runs past it), or where it began when that run starts first. That is the trim's result, recomputed on every read, so moving the start forward again restores the Reset run exactly. `longestStreakDays`, `dayCount`, `reversibleSplit` and Timeline's tree preview (`TimelineView.soberDays`) read through it. `splitClosedJourney` still splits the stored run, so an older slip keeps the Reset run's untouched tail on its rest run.
- J3's cleanup skips any day a closed run covers as stored, so the Reset run's assumed days survive the forward move. A start moved into empty history and back still loses its assumed days (`j3_aMisTapEarlierThenTheRightDateLeavesNoExtraDays` still passes).
- The moved run can later be cut short by a slip inside the Reset run's old span. A slip-closed run that ends inside a closed run still cuts it when it began inside it or ends a whole day into it on a slip day's midnight, so the Reset run keeps reading as it did after the trim (`j4_aSlipAfterTheMoveKeepsTheResetRunCut`, `j4_aSlipInsideTheResetRunsSpanKeepsItEmpty`). Two stored shapes would otherwise cut a run nobody moved, so the rule excludes them, each with a test that passes before and after: builds before 2026-09-04 closed a back-dated slip's run at the moment it was logged, inside the run the slip started (`upgrade_anOldOverlappingSlipRunDoesNotHideTheNextRun`), and Z1 re-keys a slip's midnight up to a day past the next run's start on a zone change west (`z1_aSlipEndRekeyedPastTheNextRunsStartDoesNotHideIt`). A slip-closed run is never cut itself: no start moves back past a slip.
- Read at its cut end, an onboarding leftover that began on the day a slip is back-dated to would pass for a run between the slip and the active one and refuse that slip's undo, which HEAD and 9733bc3 allow. `reversibleSplit` reads the runs after the slip as stored while the active run still starts where the back-dated slip put it (no start was moved into them), and at their cut ends otherwise, as the trim did. Guarded by `s1_aLeftoverStartedOnABackDatedSlipsDayDoesNotBlockItsUndo`.
- No stored format changed and nothing is written back: closed runs a previous build of this branch trimmed keep their trimmed end, and stores from shipped builds read as before except where a start move overlaps them.

Both verify probes are now regression tests: `j4_j3_assumedDaysOfAResetRunSurviveAStartMovedBackThenForward` (Reset run 49 to 20 days ago, rows assumed; lifetime 49 and longest 30 after the start goes to 40 days ago and back) and `j4_aResetRunsLengthSurvivesAStartMovedBackThenForward` (Reset run 200 to 20 days ago, every day tapped; longest 181 and lifetime 200 after 100 days ago and back). Their controls check lifetime and longest before and the counter after each set. Tests that checked the trim in the store (`closedRunsEndBy`) now check the runs as read.
