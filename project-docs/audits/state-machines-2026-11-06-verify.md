## Must change

1. **S1: the most recent slip can't be undone when a leftover onboarding run starts after the active run.** Builds before 2026-10-31 (`ff76571`) created a new run on every setup pass (`startJourney(at: effectiveStart)`), closing the earlier pass's run at that moment. Within one launch every pass shares a start. But a setup killed after the trial step (which persisted) and redone on a later launch starts again from `@State startDate = .now` (`OnboardingView.swift:23`). If the user re-picks an earlier date, or the same date at an earlier clock time (the date-only picker keeps the time of day), the leftover run starts after the active run and ends long before today.
   - Route: that user, months later: Home › ⋯ › I slipped › Log (or Timeline › today › Log a slip), then Timeline › today. "Change to sober" is gone. Instead the user reads "A slip can only be taken back while it's the most recent one on your record" (`TimelineView.swift:530`), although it is their only slip.
   - Cause: `reversibleSplit` refuses if any non-empty closed run has `startDate > closed.startDate` (`SobrietyService.swift:230`). The leftover run qualifies, although it ended before the slip and doesn't come after it. 9733bc3 matched on end date and allowed this undo.
   - Proof: probes `probe_leftoverRunStartingLaterSameDateThenSlipTodayIsUndoable` (leftover at 22:00, active at 08:00 on the same date) and `probe_leftoverRunStartingLaterEarlierDateThenSlipTodayIsUndoable` (leftover 90 days ago, active 100 days ago). Each asserts its preconditions first (counter 101, then 1 after the slip). On HEAD both fail at `canUndo`, `undo` and the restored count. On 9733bc3 both pass (runs below).
   - A fix that keeps every current test's meaning: only a closed run that began at or after the slip run's *end* blocks the undo, i.e. one that comes between the slip and the active run. A later slip, a Reset after the slip, and the J1 rest of a split all start at or after that end. A leftover run nested inside the slip's run does not. Turn both probes into regression tests.

## Notes

1. **Fixes doc.** Rows, test counts and run ids match what I found. Its third follow-up says the leftover run "shares the active run's start". That holds within one launch but not across a killed and redone setup, which is the gap above.
2. **N3 trade-off** (disclosed). Someone who doesn't open the app for 30 days stops getting the daily reminder until they return. 9733bc3's repeating request fired forever with frozen copy. The lapse nudge fires once at day 3. This is a product call for Jack, not a defect.
3. **Held J3 item overstates one risk.** It says moving the start later can delete a sober day tapped in a build before `wasLogged`. `migrateLegacyCheckInsIfNeeded` marked every pre-upgrade row logged (`CheckInService.swift:225`), and the deletion skips logged rows, so those taps are safe. For the cleanup question: stale rows written by builds since `wasLogged` (2026-09-03) are unlogged and can be told apart; only older ones can't.
4. **J1 split with the same legacy shape.** `splitClosedJourney` takes `journeys.first` of an unsorted fetch (`SobrietyService.swift:250`). Where a leftover run overlaps the slip run, it may split the leftover instead. The slip run then still spans the older slip, and the leftover's tail can block the newer slip's undo through the same rule. This is the same root cause as Must change 1 and depends on fetch order, so it is not separately proven. The fix there covers the undo half. Sorting or preferring the slip-closed run would cover the split.
5. **T2 on cached info.** A user who cancels, then turns renewal back on elsewhere, loses the recap banner's "dismissed" mark at the next launch (cleared by `clear()`), so the banner can show once more. Narrow and harmless.
6. **Refusal copy edge** (pre-existing). Reset today, then Timeline › yesterday › Log a slip, then Change to sober is refused with the "most recent one" copy, although it is the only slip. 9733bc3 refused it too.
7. **Watch and widgets** use only `GardenService.stage` and `cycleProgress`, which are unchanged. Snapshots are still pushed after every write.
8. **Duo.** The Timeline pane writes through the same `SlipRecorder` and `ReminderSync` paths, and C1's guard covers the stale Home beside it. No layout code changed.
9. **Coming up** on Home lists "Wed, Dec 30" twice in the demo. `MilestoneSchedule` is not in this diff.
