# UX Analysis & Suggested Improvements: Sober App (g521)

This document analyzes the Sober app codebase from a user-experience (UX) and user-operations perspective. It identifies several critical bugs, logic gaps, and functional limitations that directly impact how a user operates the application, feels rewarded, or recovers from a relapse. No code changes have been made; this is a pure analysis.

---

## 1. Visual Collision in Unlock Celebration Overlay
* **User Experience & Operation Context:**
  When a user reaches a sobriety milestone (e.g., Day 14), they are presented with a celebration card detailing their new unlock. This card is designed to build excitement and reward their progress. Under the current implementation, however, the giant white day counter (e.g., "45") and the prominent check-in buttons from the underlying dashboard show through the overlay. This causes text overlap (e.g., the milestone label colliding with the background number) and results in a cluttered, unpolished look.
* **Code Limitation:**
  In [HomeView.swift](file:///Users/jackwallner/sober/Sober/Features/Today/HomeView.swift#L114-L126), the `UnlockCelebrationView` is displayed as an `.overlay` on the main ZStack. The backdrop in [UnlockCelebrationView.swift](file:///Users/jackwallner/sober/Sober/Features/Garden/UnlockCelebrationView.swift#L13-L20) uses `.ultraThinMaterial` and `Color.black.opacity(0.55)`. This is semi-transparent, allowing high-contrast white text like the `counterOverlay` and active buttons from `HomeView` to bleed through.
* **Suggested Improvement:**
  1. Conditionally hide the main dashboard overlays in [HomeView.swift](file:///Users/jackwallner/sober/Sober/Features/Today/HomeView.swift#L52-L58) when a celebration is active:
     ```swift
     if !showCelebration {
         VStack(spacing: Theme.Space.m) {
             counterOverlay
             Spacer(minLength: Theme.Space.m)
             bottomStack
         }
     }
     ```
  2. Alternatively, style the celebration card in `UnlockCelebrationView` with a solid, opaque background panel to separate it from the underlying view.

## 2. Broken Visual History on Journey Reset (The "Active Journey" Bug)
* **User Experience & Operation Context:**
  The app tells the user: *"Your history stays, and your tree carries everything you've already grown."* However, if a user relapses (slips) on day 50 and starts a fresh journey, their active day count returns to 0. If they then go to the **Timeline** (Calendar) tab and tap on a green day from their *previous* 50-day streak, they expect to see the mature tree they had grown on that date. Instead, the tree preview at the bottom renders a Day 0 **Seed**. Wiping out the visual history of their past success makes a relapse feel like a total loss, violating the app's promise of preserving historical growth.
* **Code Limitation:**
  In [TimelineView.swift](file:///Users/jackwallner/sober/Sober/Features/Calendar/TimelineView.swift#L23-L29), the helper `soberDays(on date: Date)` calculates days solely based on `activeStart` (the currently active journey):
  ```swift
  private func soberDays(on date: Date) -> Int {
      guard let start = activeStart else { return 0 }
      let s = DateHelpers.startOfDay(start)
      let d = DateHelpers.startOfDay(date)
      guard d >= s else { return 0 } // <-- Fails for all historical dates before the current relapse reset
      return DateHelpers.daysBetween(s, d)
  }
  ```
  Any calendar date before the current active journey returns `0` days, causing the tree preview to render a seed.
* **Suggested Improvement:**
  Update `soberDays(on:)` to look up which historical journey was active on that specific date, rather than relying exclusively on the active journey. This ensures that their visual tree log is preserved for all past dates:
  ```swift
  private func soberDays(on date: Date) -> Int {
      let d = DateHelpers.startOfDay(date)
      // Find the journey that covered this calendar date
      guard let journey = journeys.first(where: { j in
          let s = DateHelpers.startOfDay(j.startDate)
          if let end = j.endDate {
              let e = DateHelpers.startOfDay(end)
              return d >= s && d <= e
          } else {
              return d >= s
          }
      }) else { return 0 }
      return DateHelpers.daysBetween(journey.startDate, d)
  }
  ```

## 3. Incomplete Check-In Flow (No Mood or Notes Entry)
* **User Experience & Operation Context:**
  Sobriety tracking is about self-reflection. Users value logging their daily mood and quick notes to spot triggers, patterns, and positive trends. Currently, tapping "Check in for today" on the dashboard instantly marks the day as sober without prompting the user. There is no way on the main screen to record notes or mood, reducing a meaningful habit to a mechanical button-click.
* **Code Limitation:**
  The `DailyCheckIn` model ([DailyCheckIn.swift](file:///Users/jackwallner/sober/Shared/Models/DailyCheckIn.swift#L8-L9)) includes `mood` and `note` fields, and [CheckInService.swift](file:///Users/jackwallner/sober/Shared/Services/CheckInService.swift#L12) is built to save them. However, in [HomeView.swift](file:///Users/jackwallner/sober/Sober/Features/Today/HomeView.swift#L208-L233), the check-in button triggers `CheckInService(context: context).checkIn()`, defaulting all parameters to `nil`.
* **Suggested Improvement:**
  Instead of an instant check-in, have the check-in button open a micro-sheet or expand inline to offer a simple 5-emoji mood selector (matching the feeling scale in the journal) and a single-line note text field. This populates the database and provides rich daily logs.

## 4. Inability to Edit or Backdate Check-Ins on the Calendar
* **User Experience & Operation Context:**
  Humans make mistakes and forget to check in. If a user forgot to open the app yesterday, that day remains grey on the calendar. Under the current UI, tapping that past day only shows the tree preview; they cannot log that they were sober yesterday. Similarly, if they accidentally click "Check in" but actually relapsed (or vice versa), they cannot delete or amend their log.
* **Code Limitation:**
  In [TimelineView.swift](file:///Users/jackwallner/sober/Sober/Features/Calendar/TimelineView.swift#L199-L203), the calendar cells contain a simple tap gesture that updates `selectedDate` but presents no controls to write or edit database entries.
* **Suggested Improvement:**
  Add a contextual management card below the calendar in [TimelineView.swift](file:///Users/jackwallner/sober/Sober/Features/Calendar/TimelineView.swift#L207-L238).
  * If the selected day has no check-in, display buttons to **"Log as Sober"** or **"Log a Slip"**.
  * If a check-in exists, display their logged mood and notes, and provide an **"Edit Log"** or **"Delete Log"** option.

## 5. Ghost "Vitality Decay" System (Broken Gamification Loop)
* **User Experience & Operation Context:**
  The app features a "watering" mechanic, and the code comments state that garden vitality decays daily. This creates a compelling gamification loop: checking in waters the garden, keeping the bonsai green and thriving. However, if a user opens the app after neglecting it for two weeks, their garden is still at 100% saturation and full vitality. The stakes of the game are visual ghosts—there is no decay, meaning watering does nothing, and the motivation loop is broken.
* **Code Limitation:**
  In [GardenState.swift](file:///Users/jackwallner/sober/Shared/Models/GardenState.swift#L7), `vitality` is defined, and [GardenService.swift](file:///Users/jackwallner/sober/Shared/Services/GardenService.swift#L74) implements a `water()` function. However, there is no system or trigger in the entire codebase that decreases `vitality`. It defaults to `1.0` and remains there permanently.
* **Suggested Improvement:**
  Implement a check on app startup (or within `refreshCheckInState`):
  * Compare the current date with the `lastWateredAt` timestamp.
  * Subtract vitality for every day missed (e.g., `-0.15` per day).
  * Update [BonsaiRenderer.swift](file:///Users/jackwallner/sober/Sober/Features/Garden/BonsaiRenderer.swift#L715) and [GardenItemRenderer.swift](file:///Users/jackwallner/sober/Sober/Features/Garden/GardenItemRenderer.swift) to visually desaturate or "wilt" elements when vitality is low, creating a tangible incentive to maintain the daily check-in habit.

## 6. Achievement Loss on Streak Reset
* **User Experience & Operation Context:**
  Achievements like "Strong Foundation" (7 days) or "Perfect Week" are permanent historical badges of honor. If a user relapses and resets their counter, their active days return to 0. In the current UI, this immediately locks all of their achievements again, making the user feel like their historical progress is entirely erased.
* **Code Limitation:**
  The [UnlockedAchievement.swift](file:///Users/jackwallner/sober/Shared/Models/UnlockedAchievement.swift) model is defined and registered in the database, but is never written to or queried. Instead, [HomeView.swift](file:///Users/jackwallner/sober/Sober/Features/Today/HomeView.swift#L407-L408) displays achievements as locked or unlocked based purely on the active journey's current day count:
  ```swift
  let unlocked = days >= a.dayThreshold
  ```
* **Suggested Improvement:**
  * Implement an achievement unlocking check during check-ins that writes to the `UnlockedAchievement` SwiftData model once a day threshold is hit.
  * Update the UI (`ProgressSheet`) to check if an achievement exists in the `UnlockedAchievement` database. This ensures earned achievements remain permanently unlocked in their trophy case regardless of relapse resets.

## 7. Aggressive Gating of Health Benefits
* **User Experience & Operation Context:**
  Sobriety trackers rely on positive health feedback to encourage users in early, difficult stages. By default, the app gates all health benefits after the first 24 hours behind the premium subscription. This means a user on Day 2 is already confronted with a locked, blurred health benefit list, making the app feel overly commercialized before trust or value has been established.
* **Code Limitation:**
  In [HealthView.swift](file:///Users/jackwallner/sober/Sober/Features/Health/HealthView.swift#L16), `freeRevealCount` is set to `2`. The first two benefits are "Blood Alcohol Clearing" (6h) and "Blood Sugar Stabilization" (24h), meaning the third benefit ("Rehydration Complete", 48h) is immediately blurred out for free users.
* **Suggested Improvement:**
  Increase `freeRevealCount` to `5` or `6`. This makes benefits up to Day 14 (such as Sleep Quality, Mental Clarity, and Reduced Anxiety) free. Free users experience the immediate physiological rewards of early sobriety, building habits, while the long-term milestones (1 month, 3 months, 1 year) remain behind the paywall to drive conversions.

## 8. Missing Journey Adjustments (Start Date & Time)
* **User Experience & Operation Context:**
  When a user starts onboarding, they select a start date. If they accidentally select the wrong date, they cannot change it. The settings panel has no input for start date, leaving the user with an permanently incorrect day counter. Furthermore, the onboarding date picker doesn't collect time, and the code coerces the journey start to midnight. For users in early recovery, tracking the exact hour of their last drink is highly meaningful, and forcing it to midnight makes hour-based health milestones inaccurate.
* **Code Limitation:**
  There is no path in [SettingsView.swift](file:///Users/jackwallner/sober/Sober/Features/Settings/SettingsView.swift) to edit `SobrietyJourney.startDate`. In [OnboardingView.swift](file:///Users/jackwallner/sober/Sober/Features/Onboarding/OnboardingView.swift#L148), the date is forced to `DateHelpers.startOfDay(startDate)`.
* **Suggested Improvement:**
  1. Add a **"Sobriety Start Date"** date-time picker to `SettingsView` so users can adjust their start timestamp at any point.
  2. Modify onboarding to collect both date and time (using a combined picker), allowing hourly tracking of early benefits to run with high precision.

## 9. Rigid Journaling Prompts
* **User Experience & Operation Context:**
  Journaling is highly personal. Sometimes a user wants to write a free-form entry about their day, or they don't resonate with the deterministic "prompt of the day". The journal compose screen currently locks them into writing about the active prompt, with no option to free-write or select a different prompt.
* **Code Limitation:**
  In [JournalView.swift](file:///Users/jackwallner/sober/Sober/Features/Journal/JournalView.swift#L104-L105), `ComposeEntrySheet` hardcodes the prompt of the day using `JournalPromptCatalog.promptOfDay()`.
* **Suggested Improvement:**
  Add a **"Shuffle Prompt"** or **"Free Write"** toggle inside the entry composer. This gives users the flexibility to express themselves freely when the daily prompt doesn't match their mindset.

## 10. Lifetime vs. Streak metrics (Preserving Financial/Caloric Progress)
* **User Experience & Operation Context:**
  Watching money and calories saved stack up is a powerful motivator. If a user relapses, resetting their day counter to 0 also resets their savings metrics to $0 and 0 calories. Wiping out these accumulated metrics exacerbates the feeling of failure.
* **Code Limitation:**
  In [HomeView.swift](file:///Users/jackwallner/sober/Sober/Features/Today/HomeView.swift#L397-L404), the money saved and calories avoided are calculated strictly using `days` (the day count of the current active journey).
* **Suggested Improvement:**
  Calculate and display **Lifetime Savings** (total sober days logged ever * cost/calories per day) alongside current streak savings. This reminds the user that their past sober weeks were not a waste of money or effort, encouraging them to pick themselves back up.

## 11. Interactive Widget Support
* **User Experience & Operation Context:**
  The widget displays their current streak and garden stage, which is a great visual reminder. However, to check in, they have to tap the widget, wait for the app to fully load, and tap the check-in button.
* **Code Limitation:**
  [SoberWidgets.swift](file:///Users/jackwallner/sober/SoberWidgets/SoberWidgets.swift) is a static view-only widget.
* **Suggested Improvement:**
  Implement an interactive widget button using iOS 17's **App Intents** framework. This allows users to tap a "Check In" button directly on their Home or Lock Screen, logging their sobriety instantly in the background without launching the full app, drastically reducing daily friction.
