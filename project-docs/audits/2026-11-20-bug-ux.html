Bugs, worst first

B1

One failed database open hides the sobriety date and every check-in for good, with no message and no way back

fixedhighplausibledata

Fixed 2026-11-20 in 862f807. Failed opens retry and never move the file while locked; the file is moved aside only when proven corrupt or after three unlocked launches, a set-aside copy is put back when the store is empty, and a Your data is safe screen replaces the empty stand-in. Tests: LocalStoreOpenerTests.

Impact

A one-off open failure turns into permanent loss of a multi-month or multi-year streak and journal, with no alert and no recovery path in the app. If the fresh store also fails, the app runs on an in-memory store and nothing saved survives a relaunch, with no warning.

How it happens
  1. Open the app on a phone where the first ModelContainer open throws for a transient reason (for example storage nearly full while a migration or WAL recovery needs space, or protected files not readable yet).
  2. DataService moves Sober.v2.store and its -wal/-shm files to .corrupt-<uuid> names and opens a fresh empty store.
  3. On the next launch the fresh store is used. The renamed files are never opened again, and nothing in the app lists or restores them.
  4. Onboarding runs again; sobriety date, every check-in, journal entries, cravings and garden are gone from the customer's point of view.
Where
Shared/Services/DataService.swift:17Shared/Services/DataService.swift:24Shared/Services/DataService.swift:30
Suggested fix

Retry the open once or twice before moving anything, quarantine only on a known corruption or migration error, and show an alert that points to the preserved copy (or restore the newest .corrupt-* file when the fresh store is still empty). Also alert when the in-memory fallback is used.

Evidence
        if let container = makeContainer(schema: schema, url: url) {
            return container
        }

        // A failed migration or half-written file can leave the store unopenable.
        // It holds the sobriety date and every check-in, and exists nowhere else,
        // so move it aside instead of deleting it, then retry with a fresh store.
        logger.error("ModelContainer failed to open; quarantining the store and retrying")
        quarantineStore(at: url)
        if let container = makeContainer(schema: schema, url: url) {

makeContainer uses try?, so every error takes the quarantine branch (DataService.swift:20-31, :67-75). There is no retry, no error check, no alert and no code that reads a .corrupt-* file. Baby Tracker already treats this as real: its Persistence.swift moves a store aside only for a corruption error and otherwise runs on a stand-in until the files are readable. Ranked high for what is lost, a streak that can be years long, not for how often it happens.

Checked by: Code read by two passes and by Claude Fable. The same pattern is in Simple GLP.

Not proven: No trigger was reproduced, and no background launch before first unlock was found in this app (only the iPhone app opens the store). The realistic triggers are an update whose data model change cannot be migrated, which would hit every customer at once, and an I/O failure such as a full disk during recovery.

B2

After a slip logged today, logging an older slip closes the new run, skips the split, halves the tree again and breaks undo

fixedmediumconfirmeddata

Fixed 2026-11-20 in e8ae066. An older slip after today's slip now splits the earlier run and leaves the tree and undo alone. Tests: anOlderSlipAfterTodaysSlipSplitsTheEarlierRun, todaysSlipStillUndoesAfterAnOlderOne, yesterdaysSlipAfterTodaysLeavesNoStub.

Impact

The check for 'a newer slip already restarted the counter' compares the active run's start day with tomorrow. After a slip logged today the active run starts today, so the check fails and the older slip is treated as the newest one. It closes the brand new run as a zero-length slip run, opens another, runs the garden's slip rule a second time (overwriting the undo snapshot of today's slip) and never splits the 100-day run at the older slip. Best streak then keeps counting through the older slip (101 instead of 51). Today's slip also stops being undoable correctly: the undo reopens the empty stub run, so the counter reads Day 1 instead of Day 50 and the garden snapshot restored is the wrong one. A user who slips today and then remembers an earlier slip is the normal way to hit this; the same thing happens for yesterday's slip.

How it happens
  1. Start a run 100 days ago (onboarding start date, or Settings > Sobriety Start).
  2. Home > I slipped, pick today, Log it. The counter restarts at Day 1 and the new run starts at the current moment (not tomorrow's midnight, because the start is clamped to now).
  3. Timeline > select a day 50 days ago > Log a slip (or the same sheet from Home with an older date).
  4. Read Best streak, then select today on Timeline and tap Change to sober.
Where
Shared/Services/SlipRecorder.swift:84Shared/Services/SlipRecorder.swift:94Shared/Services/SobrietyService.swift:231
Suggested fix

In SlipRecorder.record, treat the active run as already restarted when it began on or after the latest slip day (compare startOfDay(active.startDate) >= startOfDay(latestSlip) and the run was opened by a slip), instead of comparing against tomorrow's midnight, which a slip logged today can never reach because the new run's start is clamped to now. Then the older slip goes through splitClosedJourney and leaves the garden alone.

Evidence
let latestSlip = checkIns.lastSlipDate() ?? day
let restartFrom = max(DateHelpers.startOfDay(day), DateHelpers.startOfDay(latestSlip))
let dayAfter = Calendar.current.date(byAdding: .day, value: 1, to: restartFrom) ?? day
let alreadyRestarted = sobriety.activeJourney().map {
    DateHelpers.startOfDay($0.startDate) >= DateHelpers.startOfDay(dayAfter)
} ?? false
if !alreadyRestarted {
    let fresh = sobriety.resetJourney(startingAt: dayAfter, endingPreviousOn: day)

Traced by hand with today's slip first. First record(on: today): dayAfter is tomorrow midnight, resetJourney clamps the new run's start to now, so the active run starts today. Second record(on: D, older): lastSlipDate is still today, so restartFrom is today and dayAfter is tomorrow; the active run's start day (today) is not >= tomorrow, so alreadyRestarted is false. resetJourney then sets the active run's endDate to max(start, min(D, now)) = its own start and marks it 'slip', and opens a third run. splitClosedJourney is only called in the alreadyRestarted branch, so the 100-day run ends at today's midnight unsplit; longestStreakDays reads it as 101. garden.recordSlip also runs, and carryoverBeforeSlip is overwritten with the already-slipped carryover. In reversibleSplit both the old run and the stub end on today; the candidate is the one with the later start, the stub, so undo reopens the stub. The existing tests (j1_*, anOutOfOrderSlipDoesNotRewindTheCounter) all use a newest slip at least one day old, where the new run starts at tomorrow-midnight-or-earlier and the check passes, so none covers this.

Checked by: Five tests failed as predicted on a GitHub Mac (gh-sim run repo-imac8553-1120-102111-16427): after a slip today and then a slip 50 days back, the best streak reads 101 where 51 is right, a zero-length run is left behind, the tree is charged a second time, and undoing today's slip gives a count of 1 where 50 is right. Slip today then slip yesterday leaves the best streak one day long too. Claude Fable traced the same result by hand: the new run starts now (SobrietyService.swift:231), so the alreadyRestarted check at SlipRecorder.swift:79-81 compares today with tomorrow and fails.

B3

A usage-based Bloom+ pitch can fire while Home's own sheet is open, and the paywall sheet is attached one level higher

fixedmediumplausiblepurchase

Fixed 2026-11-20 in 046abea. Passive pitches wait while Home has a sheet, cover or celebration up. Test: PassivePitchHostTests.

Impact

Either the pitch lands on top of a note the user is writing or on the craving screen, or SwiftUI cannot present a second sheet from an ancestor and drops it. In the dropped case showTrialPaywall stays true, so later locked-feature taps (true to true) never open the paywall for the rest of the session, and isPresentingSheet stays true so the review prompt is also blocked. Both break the funnel; the first also interrupts the one flow the docs say must never see a paywall.

How it happens
  1. Use the free app until TrialNudgeGate.canShow() is true (48 hours or more since the last pitch) and the trial offer is available.
  2. Tap Check in for today for the third time or later (checkInCompletedCount >= 3). Home opens CheckInDetailSheet at once (HomeView.swift:586).
  3. Start typing a note. After 2.5 seconds evaluateUsageBasedTrialPitch requests the pitch.
  4. MainTabView sets showTrialPaywall = true on the TabView while Home's sheet is still up. The same race exists for the 6 second Home nudge (HomeView.swift:192) when the user has opened Settings, Progress or the craving cover inside those 6 seconds.

Suggested fix

Have handleTrialPitch skip (and clear showTrialPaywall) when any Home sheet or the craving cover is up, or publish a single 'something is presenting' flag that Home sets and the passive nudges read, as isHomeClear already does for the what-to-fix alert.
