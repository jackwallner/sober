# Fixes for the Sober state machine review, 2026-11-06

Fixes for every claim [the review](state-machines-2026-11-06-review.md) marked CONFIRMED or CONFIRMED-MINOR, plus the two reminder bugs it found that [the audit](state-machines-2026-11-06.md) missed, in the review's ranked order.

**Summary: 19 in-scope claims (6 CONFIRMED, 11 CONFIRMED-MINOR, 2 missed by the audit). 19 fixed, 0 held, 0 skipped, 0 disputed. Second verify pass: 1 regression (J4 floor with Z1), fixed. Third verify pass: 1 regression (S1 undo rule with J4's trim), fixed. 2 NOT A BUG left alone (J2, K1).** One follow-up decision is listed under "Held for Jack". [The regression check](state-machines-2026-11-06-verify.md) rejected the first J4 fix, then (second pass) the J4 floor combined with Z1's re-key, then (third pass) S1's undo rule combined with J4's trim; all three are fixed below.

**Commits.** The first run was interrupted before it committed, so every fix landed together in "chore: work left uncommitted by fleet-run 20261106-165038-430b-claude"; this branch builds on that commit, so it was not split after the fact. A second pass reviewed that code and fixed one regression it introduced in "fix: only a newly seen trial may raise the notification prompt": the T1/T3 resync runs on every Home visit and could raise the notification prompt there. Now only the first sync of a newly seen trial may prompt; later syncs only check permission (`t1_reminderIsScheduledOncePermissionArrivesLater` asserts one prompt).

Regression tests live in `SoberTests/StateMachineFixTests.swift`. Each test name starts with its claim id. The audit's repro tests the review called sound are kept there as written; J2's (an opinion against a documented rule) is not. The repro suite itself was never added to the test target.

## Held for Jack

- **Repair for users who already hit J3.** The fix stops new stale rows. Users who moved their start later before this build still have assumed rows before their first run, inflating lifetime days, money and calories, and Timeline can't reach them. Those rows can't be told apart from real taps logged by builds before `wasLogged` existed, so a cleanup could delete check-ins a long-time user really made. The same limit applies to the fix itself: when a user moves the start later, a sober day they tapped in a build before `wasLogged` (added 2026-09-03), with no mood or note, falls inside the dropped range and goes with the assumed rows. Decision: run a one-time cleanup of unlogged, mood-less, note-less rows before the earliest run start, or leave existing data as it is?

Not held, but worth knowing: N3's fix queues 30 days of dated reminders. Someone who doesn't open the app for 30 days stops getting the daily one until they return (the lapse nudge still reaches them at day 3). A repeating request can't carry changing copy, so this was the trade.

## Regression check follow-up

[The verify pass](state-machines-2026-11-06-verify.md) failed J4: its floor also stopped at a Reset and at the leftover closed run of a double onboarding, so after Home › Reset counter the start could not be moved earlier in Settings, and long-time users with the leftover run could never back-date. Fixed in "fix: only a logged slip floors the start date, a Reset run is trimmed instead". `earliestStartDate` now counts only slip-closed runs and `lastSlipDate`; `updateStartDate` trims any closed run still going at the new start to end there (a run that began later ends where it began). Both probe routes are now regression tests, plus the mistaken-Reset repair. The verify doc's bookkeeping note (stale `COMMIT_TRIAL` and `ede3cf3` references) is corrected above by citing commit subjects.

## Second regression check follow-up

[The second verify pass](state-machines-2026-11-06-verify.md) found one crash: after "I slipped" on yesterday and a zone change west within the first hours of the day, Z1 re-keys the new run's start to the new zone's midnight of that date, which is after now. `earliestStartDate()` returned `min(bound, active.startDate)`, both later than now, and `SettingsView.swift:64` built `earliest...Date.now`, which traps. Fixed in "fix: keep the Settings start floor at or before now after a zone change": `earliestStartDate(now:)` returns `min(bound, active.startDate, now)` (`Shared/Services/SobrietyService.swift:83`). The re-key itself is left as is: the run's start stays on its calendar day, as the rows do, and the counter reads that day honestly. The probe is now `j4_theStartFloorNeverPassesNowAfterAZoneChange`, built on the state the re-key leaves (a slip-closed run ending today, the active run starting at the next midnight), with a control that the start is after now.

## Third regression check follow-up

[The third verify pass](state-machines-2026-11-06-verify.md) found that S1's undo rule and J4's trim together refused the next slip's undo. `trimClosedJourneys` leaves a Reset or leftover onboarding run that began after the moved start empty on its own start, the latest start of any closed run, and `reversibleSplit` took it as "the run before" and refused because no slip closed it. While turning its probes into tests, a control turned up a second route with the same cause and no start move. The run older onboarding builds left behind shares the active run's start and ends at the moment setup ran, so it sorted after the active run once a slip closed that run on an earlier day. Route: a user who onboarded before 2026-10-31 logs a forgotten slip from before their setup date, then undoes it. 7199ab0 matched on the end date and allowed that undo. Fixed in "fix: let a slip be undone past a Reset or leftover onboarding run". `reversibleSplit` now takes the slip-closed run ending on the day, and refuses only if another closed run began after it. Empty runs not closed by a slip are passed over (`Shared/Services/SobrietyService.swift`, `reversibleSplit`). All four S1 tests still refuse their routes, because a later slip or a Reset always starts a run after the slip's run. The verify pass's three probes are now `j4_s1_` tests. Two more were added: `j4_s1_aBackDatedSlipBeforeTheTrimmedRunIsUndoable` (a slip back-dated before the trimmed run's start) and `s1_aLeftoverOnboardingRunDoesNotBlockUndoOfASlipBeforeSetup`. The control `control_leftoverOnboardingRunThenSlipTodayIsUndoable` covers the no-move case.
